# Решения (ADR-журнал)

Формат: **проблема → решение → почему → цена**. «Открытых решений» нет:
каждая строка закрыта выбором и кодом.

## P0-A. Роли и регистрация

### 1. Открытый sign-up выдавал ADMIN

**Проблема.** `User.role` имел `@default("ADMIN")`, а Better Auth принимал
`role` из тела запроса. Любой незнакомец получал полные права.

**Решение.** Три слоя:
1. `User.role @default("VIEWER")` в Prisma.
2. В Better Auth `additionalFields.role.input: false` — поле не принимается
   от клиента; `defaultValue: "VIEWER"`.
3. `databaseHooks.user.create.after` вызывает `applySignupRolePolicy`, который
   безусловно фиксирует VIEWER (кроме bootstrap, см. п. 2).

**Почему.** Одного `input: false` мало: при прямом создании пользователя
(импорт, скрипт, будущие плагины) дефолт схемы может быть другим. Слой 3 —
defense in depth и одновременно точка bootstrap.

**Цена.** Два дополнительных UPDATE на регистрацию (один обычно no-op).
Первый пользователь пустой БД всё равно становится ADMIN.

### 2. Bootstrap пустой БД

**Проблема.** Если просто запретить ADMIN при регистрации, свежая установка
остаётся без администратора — управлять нечем.

**Решение.** `applySignupRolePolicy` выполняет один атомарный
`UPDATE "User" SET role='ADMIN' WHERE id=? AND NOT EXISTS (SELECT 1 FROM "User" WHERE role='ADMIN')`.
При параллельных регистрациях ровно один UPDATE изменит строку; остальные
увидит уже существующего ADMIN и останутся VIEWER.

**Почему.** Один SQL-стейтмент атомарен в SQLite/Postgres, не требует
распределённых блокировок и не оставляет окна «два первых админа».

**Цена.** Роль нельзя выбрать при регистрации — только повышение из UI
администратором. Это осознанно.

### 3. Инварианты смены роли

**Проблема.** Понижение последнего ADMIN или смена собственной роли
блокирует систему навсегда.

**Решение.** `setUserRole` (src/lib/roles.ts) в транзакции:
- `targetId === actorId` → `OwnRoleChangeError` → tRPC `FORBIDDEN`;
- demote ADMIN выполняется условным
  `UPDATE ... WHERE role='ADMIN' AND (SELECT COUNT(*) FROM "User" WHERE role='ADMIN') > 1`;
  0 строк → `LastAdminError` → `CONFLICT`.

**Почему.** COUNT вычисляется в момент записи, а не до неё: две параллельные
смены сериализуются SQLite, вторая видит уже одного админа и отказывает.
Проверка «прочитать, потом записать» оставляла гонку.

**Цена.** Demote — raw UPDATE + ORM-дозапись для `@updatedAt`. Роутер ловит
доменные ошибки и переводит в tRPC-коды.

### 4. e2e-БД пересоздаётся на каждом старте

**Проблема.** `e2e.db` накапливал пользователей от прошлых прогонов: старые
sign-up создали десятки ADMIN, инвариант «последний администратор» переставал
быть проверяемым.

**Решение.** `tests/e2e/serve.mjs` удаляет `prisma/e2e.db*` перед
`prisma db push` + seed.

**Почему.** Тесты прав обязаны стартовать с известного baseline; иначе они
проверяют накопленный мусор, а не код. Это же требование «зелёное на свежей
БД».

**Цена.** Данные между прогонами не сохраняются (и не должны). Файлы в
`public/uploads` остаются, но тесты используют уникальные имена.

## Прежние «открытые решения»

### 5. Редиректы не исполнялись

**Решение.** Исполнение переносится в `src/proxy.ts`: точный матч pathname,
только `isActive`, 301/302, TTL-кэш 30 с с инвалидацией при мутации.
Валидация: `toPath` только относительный (`/...`, не `//`, не `/\`),
`fromPath ≠ toPath`, запрет служебных путей, цепочки ≤ 3 и без циклов.
`hits` инкрементится на сервере атомарно; tRPC `incrementHit` удаляется.

**Почему.** Proxy выполняется до рендера и не зависит от клиентского JS;
невалидируемый `toPath` — это open redirect, а публичная mutation накрутки
счётчика — фальсификация аналитики.

**Цена.** Кэш 30 с означает, что изменение редиректа применяется с задержкой
до 30 с (инвалидация — при мутации через приложение).

Реализация: пакет P1-A.

### 6. SCHEDULED не публиковался

**Решение.** `publishDue(now)` (`src/lib/publish-due.ts`): одна транзакция
находит все `SCHEDULED` с `scheduledFor <= now` и для каждой переводит
`SCHEDULED → PUBLISHED` условным `updateMany` (фильтр по статусу и дате) +
`publishedAt` + ревизия (`snapshotJson`, `changeNote: "Публикация по
расписанию"`, `authorId` владельца записи). Вебхук `entry.published` —
только после коммита (fire-and-forget, как в entry.publish).
Триггеры: `POST /api/cron/publish-due` с `CRON_SECRET` (`Authorization:
Bearer`, сравнение SHA-256 + `timingSafeEqual`; без секрета — fail closed
503) и опциональный интервал в `src/instrumentation.ts`
(`PUBLISH_DUE_TICK_MS`, выключен по умолчанию, в edge не стартует).
Время — явный параметр `now` (в проде `new Date()`, UTC ISO-8601).

**Почему.** Планирование без исполнителя — заглушка. Условный флип внутри
транзакции гарантирует: параллельный двойной прогон публикует запись ровно
один раз (второй видит PUBLISHED и пропускает) — ровно 1 ревизия, 1 вебхук.
Повторный прогон ничего не находит — идемпотентность бесплатно. Время явным
параметром вместо `Date.now()` внутри: тесты фиксируют `now` напрямую —
сильнее и стабильнее, чем fake timers поверх реальных SQLite-сокетов
(интеграция идёт на настоящей БД и настоящем echo-сервере).
Fake timers используются там, где уместны: тест регистрации интервала
`instrumentation.register()` (планирование тиков без их исполнения).

**Цена.** В self-hosted без внешнего cron нужен включённый интервал; при
нескольких инстансах возможны лишние тики (идемпотентность их гасит).
Ревизия приписывается владельцу записи (системного пользователя нет —
это осознанно: авторство контента сохраняется).

Реализация: пакет P1-B.

### 7. Нет `task.remove`

**Решение.** `task.remove` (`protectedProcedure` + проверка): автор задачи
(`assigneeId === self`) или привилегированная роль (ADMIN/MANAGER). VIEWER
чужую задачу удалить не может (`FORBIDDEN`), несуществующая — `NOT_FOUND`.
Кнопка удаления в календаре (с `confirm()`), сервер решает окончательно.

**Почему.** Созданную задачу нельзя было убрать — таблица росла мусором.
Авторство, а не только роль: VIEWER может быть исполнителем и должен уметь
убрать свою задачу, но не чужую.

**Цена.** Удаление без корзины (задача — операционный объект, не контент).

### 8. Нет UI редактирования коллекций

**Решение.** Inline-редактирование карточки: `name` и `description`
(`collection.update`, только ADMIN; кнопка видна только ADMIN).
`slug` в форме — только текст: после создания read-only и в API
(вход `update` slug не принимает), и в UI.

**Почему.** Slug — часть URL Headless API (`/api/v1/{collection}`); его смена
ломает интеграции и опубликованные ссылки. Переименование отображаемого имени
безопасно.

**Цена.** Опечатку в slug нельзя исправить из UI — только миграцией/скриптом
с пониманием последствий.

### 9. Headless-ключи в query и безлимитные ручки

**Решение.** `?key=` удалён: ключ принимается только из `x-api-key` или
`Authorization: Bearer` (query оседает в логах/CDN). READ-ключ видит только
PUBLISHED (как и раньше), запись — 403. `lastUsedAt` перезаписывается не чаще
раза в минуту (телеметрия, а не часы: каждый GET не должен дёргать строку).
Token bucket в памяти (`src/lib/rate-limit.ts`, `now` явным параметром):
`/api/v1/*` — 240/мин на IP, `/api/upload` — 60/мин на пользователя;
превышение — 429 + `Retry-After` в секундах. In-memory осознанно:
single-instance SQLite, у каждого инстанса свой бюджет (fail-open в сторону
доступности; аутентификация от лимита не зависит). Карта ведер ограничена
10 000: при активном флуде уникальных IP сначала удаляются просроченные,
затем самые старые ведра. Вытесненный ключ получает свежий бюджет — это
осознанный fail-open, зато память процесса не растёт без предела.

**Почему.** Ключ в URL — утечка по дизайну; безлимитные ручки — флуд, перебор
и забивание диска.

**Цена.** In-memory бюджет не делится между инстансами; легитимный всплеск
сверх лимита получит 429 и должен повторить после `Retry-After`. При
переполнении карты старейшее ведро может быть вытеснено и временно получить
полный бюджет: это цена защиты от неограниченного роста памяти, а не
граница аутентификации.

### 10. Загрузки: только реальные файлы под случайными именами

**Решение.** `validateUploadFile(file, bytes)` — сигнатура файла обязательна:
PNG/JPEG/GIF/WEBP/PDF/MP4 + AVIF/WEBM проверяются по magic bytes реальных
байтов (нулевой/текстовый контент под видом картинки — 400). Имя на диске —
всегда `randomUUID().ext` (коллизий, traversal и утечек имён нет); в БД
оригинальное имя хранится только для отображения (экранируется React, в путях
не используется). `sizeBytes` — реальные байты, не заявление клиента.
`media.create` (прямая запись) валидируется тем же модулем: URL обязан быть
`/uploads/<folder>/<uuid>.<ext>` из управляемого набора, mime — соответствовать
расширению, размер — в лимите. SVG/HTML/JS по-прежнему запрещены (stored XSS
в origin CMS).

**Почему.** Расширение и MIME подделываются одной строкой; без magic check
«картинка» с HTML-внутреностями ложится в `/uploads` и отдаётся с тем же origin. Произвольный `media.create` позволял записать любой URL
с любым mime/size в обход всех проверок загрузки.

**Цена.** Нестандартные, но валидные файлы с повреждёнными заголовками
отклоняются; AVIF требует `ftyp`+`avif`-бренд (обычный mp4 под видом avif
не проходит).

### 11. P3: a11y/контраст/скриншоты

**Решение.** `@axe-core/playwright` — dev-зависимость (обоснование: пакет P3
требует axe-проверку «0 serious/critical»; в рантайм не попадает).
Скриншоты: 12 страниц × 3 вьюпорта (375/768/1440) × светлая/тёмная тема —
72 + empty/skeleton, итого 74 файла в `test-results/screenshots/` (gitignore,
в индекс не попадают). Проверки в `tests/e2e/visual-a11y.spec.ts`:
- нет горизонтального скролла на каждой комбинации (documentElement);
- axe: 0 serious/critical на каждой странице в обеих темах (включает
  color-contrast ≥4.5:1 для обычного текста);
- empty state и skeleton коллекций (перехват tRPC: пустой список / задержка);
- клавиатура: Tab-порядок без потери фокуса, фокус-кольцо `#f97316`
  (`:focus-visible` в globals.css, проверено по computed style);
- Esc закрывает командную палитру (Ctrl+K открыть);
- dnd-kit KeyboardSensor на `/board` (Space — взять, Esc — отмена) и ручки
  сортировки в билдере (`title`+`aria-label`).

**Контраст: палитра текста.** Белый текст на фирменном `#f97316` даёт 2.8:1 —
ниже AA, поэтому все текстовые CTA-поверхности переведены на тёмный оттенок
того же hue: `bg-[#c2410c] hover:bg-[#9a3412]` (белый текст 5.0:1).
Оранжевый текст на светлом: `text-[#9a3412] dark:text-[#f97316]`
(тёмная тема оставлена как была — там контраст и так проходит).
Красный текст: `text-red-600 dark:text-red-500`. Всегда-тёмные auth-страницы
(`bg-[#12121a]`) не трогали — там `#f97316`-текст проходит.
Исправлены по ходу 3 настоящих переполнения: `min-w-0` на main (grid blowout),
на flex-враппере таблицы коллекций и на aside календаря; `min-w-0 w-full`
на селектах формы задач; `min-w-0` на кнопках-днях календаря.

**Почему.** Оранжевый бренд остаётся для акцентов/колец/бейджей-фонов, но
текст обязан читаться по WCAG AA. axe — арбитр: список выше — это ровно то,
что он флаговал, плюс labels/selects (`select-name`, `label`,
`label-title-only`, `label-content-name-mismatch` — всем контролам даны
доступные имена).

**Цена.** CTA-кнопки темнее фирменного чипа (тот же hue, темнее оттенок);
`@axe-core/playwright` тянет браузерный axe-core в dev-зависимости.

### 12. P4: чистая установка обязана работать с первого раза

**Решение.** `better-sqlite3` зафиксирован на `^12.11.1` (единственная
дедуплицированная копия; nested-дубль от адаптера исчез).
v13 поставляет bundled prebuilds с `gypfile:false`, но npm всё равно
синтезирует `node-gyp rebuild` при наличии `binding.gyp` и падает на машинах
без VS Build Tools — чистый клон на Windows не ставился вообще. У v12
`prebuild-install || node-gyp rebuild` скачивает готовый бинарник
(проверено: exit 0). Версия совпадает с той, что резолвит себе
`@prisma/adapter-better-sqlite3@7.10.1`, сырой импорт (`new Database`)
используется только в одном e2e-сидтесте и с v12 совместим.
Плюс хуки `predb:seed`/`predev` → `prisma generate`: README-поток
`db:push → db:seed` падал на чистой копии (`Cannot find module
.prisma/client/default`). CI (`ci.yml`) выполняет ровно ворота
`test:all` (typecheck + vitest + build + e2e) после `npm ci` и установки
Chromium.

**Почему.** P4 требует зелёный `test:all` на голом клоне; зависимость,
требующая компилятор C++ на машине разработчика, — скрытый стопор.
Дефект всплыл только на чистой копии (в рабочем дереве node_modules был
собран раньше).

**Цена.** Остаёмся на v12 вместо v13 (N-API, разницы в используемых API нет);
`npm ci` тянет prebuild через сеть (как и любой пакет).

Dependabot повторно предложил v13 (`2a331c4`); при проверке установки
на Windows `npm install` снова упал на `node-gyp rebuild` без VS Build Tools,
поэтому версия возвращена к `^12.11.1`. ADR остаётся в силе: обновление
до v13 допустимо только вместе с решением проблемы prebuild на Windows.

### 13. Публичные страницы соответствуют sitemap

**Решение.** Реализованы RSC-маршруты `/c/[slug]` (список коллекции) и
`/p/[collection]/[slug]` (запись). Оба читают только `status = PUBLISHED`:
черновики, записи вне публикации и несуществующие slug'и отдают `404`.
Запись рендерит только видимые блоки (`isVisible`, `order asc`) через
`BlockRender`, показывает дату публикации и теги; `generateMetadata`
использует `seoTitle`/`seoDescription`/`ogImageUrl`/`canonicalUrl`/`noIndex`.
Запросы обёрнуты в React `cache()`, чтобы `generateMetadata` и рендер не
делали два одинаковых чтения. Список коллекции — первые 50 опубликованных
записей, новые сверху.

**Почему.** `sitemap.xml` уже публиковал `/c/` и `/p/`, но маршрутов не было:
поисковики и пользователи получали 404. Продукт — CMS с публичной доставкой,
поэтому чинить нужно страницами, а не удалением URL из карты сайта.

**Цена.** Публичные страницы читают SQLite на каждый запрос (без ISR);
при росте трафика понадобится `revalidate`/кэш. Список ограничен 50
записями без пагинации.

### 14. CI не зависит от apt при установке Chromium

**Решение.** В `ci.yml` используется `npx playwright install chromium` без
`--with-deps`: образ `ubuntu-latest` уже содержит системные библиотеки.
`--with-deps` каждый раз ходит в `archive.ubuntu.com`; при DNS-сбое раннера
job падает до запуска тестов (наблюдалось дважды подряд).

**Почему.** Установка браузера не должна быть точкой отказа CI из-за
чужого apt-зеркала.

**Цена.** Если GitHub уберёт библиотеки из образа, шаг придётся вернуть
или ставить зависимости точечно.

### 15. Статические проверки: ESLint + покрытие в общих воротах

**Решение.** Добавлен ESLint 9 с flat-config `eslint.config.mjs`:
`eslint-config-next/core-web-vitals` + `eslint-config-next/typescript`.
`npm run lint` включён первым шагом `test:all`, поэтому CI проверяет его
до типов и тестов. Покрытие (`@vitest/coverage-v8`, `npm run test:coverage`)
тоже включено в `test:all`; отчёт считает весь `src`, пороги —
45% statements/lines, 42% branches, 32% functions. UI-страницы остаются
преимущественно за e2e (83 сценария: рендер, 404, axe, скриншоты,
клавиатура), поэтому общий процент ниже серверного слоя.

TypeScript 7 не предоставляет API для typescript-eslint. Использован
официальный side-by-side рецепт из анонса TS 7: `typescript` — npm-алиас
на `@typescript/typescript6` (API для ESLint/Next), `@typescript/native` —
алиас на `typescript@7`, который даёт быстрый `tsc`. `npm run typecheck`
по-прежнему идёт через TS 7 (`npx tsc --version` → 7.0.2).

**Почему.** До этого в проекте не было линтера, а `next build` в Next 16
больше не запускает ESLint автоматически: ошибки React hooks/Next правил
могли попасть в main незамеченными. Покрытие без порога — отчёт, который
никто не обязан читать; порог превращает его в проверку.

**Цена.** ESLint и typescript-eslint добавляют dev-зависимости и ~10 с к
прогону. Порог покрытия может потребовать теста при добавлении крупного
непокрытого модуля — это осознанно. Алиас `typescript` на TS 6 нужен
только инструментам; сборка/типы используют TS 7. Для устранения
moderate-уязвимости `minimatch@10` (DoS через globparts) добавлен точечный
npm-override `@typescript-eslint/typescript-estree → minimatch@^11.0.8`;
`npm audit` снова даёт 0 уязвимостей.

### 16. P0/P1: демо-доступы, секрет и инварианты записи

**Проблема.** `db:seed` создавал на любом инстансе ADMIN с общеизвестным
паролем, а форма входа подставляла его в поля; production принимал короткий
или демо-секрет auth. `apiKey.list/create` возвращали `keyHash` клиенту.
`/api/upload` читал тело целиком до проверки размера и оставлял файл-сироту
при ошибке БД. `entry.update` мог поставить `PUBLISHED` без `publishedAt`;
`entry.publish` не был транзакционным/идемпотентным; блоки и теги писались
без транзакции; CSV/Headless-импорт обходили ревизию/activity и превращали
любую ошибку БД в 409; откат ревизии восстанавливал только title/fields/slug;
`?next=` после входа игнорировался. Статусы и `targetState` принимались
произвольными строками.

**Решение.**
- Демо-доступы вынесены в `src/lib/demo-access.ts`. Seed на production
  требует явного `SEED_ALLOW=1`; форма входа подставляет креды только вне
  production. `VERSO_TEST_HARNESS=1` — отдельный флаг e2e-харнесса (не
  переиспользует `AUTH_RATELIMIT`), а `BETTER_AUTH_SECRET` в проде обязан
  быть ≥32 символов и не содержать `change-me`/`test`/`demo`.
- API-ключи: `keyHash` никогда не покидает сервер (`select` безопасных
  полей), `expiresAt` валидируется до записи, сырой ключ возвращается один раз.
- Загрузка: ранний отказ по `Content-Length`, затем по `File.size`, затем по
  фактическому буферу; при ошибке `mediaAsset.create` файл удаляется через
  `removeManagedUpload` (тот же путь-страж используется `media.remove` и
  `deleteMany`).
- Инварианты записи: `update` с `PUBLISHED` проставляет `publishedAt` только
  если даты ещё нет; `publish` — одна транзакция (статус + дата + ревизия +
  activity) и идемпотентен; `entry.published` летит только на переходе в
  `PUBLISHED`, правки уже опубликованной записи — `entry.updated`.
- `block.upsertMany`, `entry.setTags` и импорты выполняются в транзакциях.
  CSV проверяет `authorId` (404 вместо P2003) и создаёт ревизию v1 + activity
  на каждую строку; построчный fallback срабатывает только на P2002, прочие
  ошибки не глотаются. `POST /api/v1/{collection}` следует тем же правилам,
  маппит в 409 только P2002, остальное — 500.
- Откат ревизии восстанавливает полный скалярный снапшот (SEO, статус,
  даты, этап, теги), сохраняя уникальность slug; старые снапшоты без тегов
  не стирают текущие связи. `safeInternalPath` — единый страж для
  SEO-редиректов proxy и `?next=` формы входа.
- `EntryStatus`/`TaskStatus`/`TaskPriority`/`targetState` — Zod-enum;
  мусор отклоняется до БД.

**Почему.** Демо-пароль и секрет — прямой захват сессий/админки; `keyHash`
не нужен клиенту и расширяет поверхность атаки; размер, проверенный после
`formData()`, уже не защищает память; частичные записи и «проглоченные»
ошибки создают тихие потери данных; открытый `?next=` — классический
open redirect.

**Цена.** `entry.published` больше не дублируется при каждом сохранении
живой записи — интеграциям, которым нужны правки, следует слушать
`entry.updated`. Импорт CSV стал медленнее (ревизия + activity на строку).
При удалённом этапе откат оставляет текущий этап, а старые снапшоты без
тегов не восстанавливают теги (их там просто нет). `Content-Length`
используется только как ранний фильтр: фактический размер всё равно
перепроверяется по буферу.

### 17. Хвосты P1: снапшот расписания, секреты вебхуков, время и теги

**Контекст.** После пакета P1 остались четыре несогласованности того же
класса, что и закрытые инварианты: `publishDue` писал снапшот в старом формате
(блоки дублировались внутри `entry`, теги отсутствовали), `webhook.list` и
`webhook.toggle` возвращали HMAC-секрет, `scheduledFor` нельзя было снять и он
парсился в TZ сервера, а `entry.setTags` менял теги без ревизии/activity.

**Решение.**
- `publishDue` строит снапшот общим `buildEntrySnapshot` (скаляры без
  relations + блоки + имена тегов), пишет activity `PUBLISHED` и отправляет
  теги в payload вебхука — форма и аудит совпадают с `entry.publish`.
- `webhookRouter` (`list`/`create`/`update`/`toggle`/`remove`) отвечает только
  через `WEBHOOK_SAFE_SELECT`; сохранённый `secret` нельзя прочитать через
  tRPC. Особенно важно для `toggle`: это `editorProcedure`, и раньше MANAGER
  получал секрет в ответе на переключение.
- `entry.update` принимает `scheduledFor: string | null`: `null` явно снимает
  расписание, `undefined` оставляет как есть. UI (`EntryForm` и конструктор)
  конвертирует `datetime-local` → UTC ISO через `src/lib/datetime.ts` и
  показывает обратно локальное время браузера.
- `entry.setTags` сравнивает набор тегов до и после. При изменении пишется
  ревизия «Изменение тегов», activity `TAGS_CHANGED`, после коммита —
  `entry.updated`; несуществующая запись даёт `NOT_FOUND`. Повторный вызов с
  тем же набором не создаёт ревизию и не дублирует вебхук (форма вызывает
  `setTags` после каждого сохранения).

**Почему.** Ревизия, из которой нельзя восстановить теги, — это не история,
а её имитация; секрет подписи в ответе MANAGER'у ломает доверие к HMAC;
время без offset публиковало запись не тогда, когда его выбрал пользователь;
изменение тегов без ревизии и события было тихим обходом аудита.

**Цена.** Секрет вебхука нельзя прочитать после создания — только задать
новый. `setTags` делает дополнительное чтение записи в транзакции, зато не
плодит шум в истории. Время хранится в UTC, отображается в TZ браузера.

### 18. Надёжность SQLite: миграции, индексы и PRAGMA

**Контекст.** Схема жила через `prisma db push`: на чистой машине это
работало, но не давало истории изменений, проверяемого апгрейда существующей
БД и отката. Индексы были только у `Entry(status, publishedAt)`,
`PageBlock(entryId, order)` и `Revision(entryId, version)`, хотя дашборд
сортирует по `updatedAt`, планировщик ищет `SCHEDULED` по `scheduledFor`, а
лента activity — по `entryId + createdAt`. SQLite-соединение не задавало
явно `journal_mode`, `synchronous` и `foreign_keys`: поведение зависело от
сборки better-sqlite3 и окружения.

**Решение.**
- `prisma/migrations/20261114000000_baseline` — снимок текущей схемы
  (`migrate diff --from-empty`), `20261114000100_indexes` — только
  `CREATE INDEX`. Обе миграции применяются через `prisma migrate deploy`.
  Существующая БД (например, локальный `dev.db`) получает baseline через
  `migrate resolve --applied` только после проверки, что diff до текущей
  схемы содержит лишь `CREATE INDEX` из индексной миграции (иначе — drift).
- Индексы добавлены под реальные запросы: `Entry(status, scheduledFor)` для
  `publishDue`; `Entry(collectionId, status, updatedAt)` и
  `Entry(collectionId, updatedAt)` для списков/CSV; `Entry(updatedAt)` для
  календаря; `Entry(stageId)` для канбана; `Entry(collectionId, status,
  publishedAt)` для публичной выдачи; `EntryTag(tagId)`;
  `ActivityLog(entryId, createdAt)`; `EditorialTask(dueDate/entryId/
  assigneeId)`; `MediaAsset(folder, createdAt)`; auth-таблицы по `userId`,
  `providerId+accountId`, `identifier`; `WebhookEndpoint(isActive)`.
- `src/lib/prisma-client.ts` оборачивает адаптер и выполняет на открытом
  соединении `journal_mode=WAL`, `synchronous=NORMAL`, `foreign_keys=ON`,
  `busy_timeout=5000` до первого запроса. Тесты используют ту же фабрику, а
  не отдельный `new PrismaClient`, поэтому проверяют production-поведение.
- `db:migrate` = `prisma migrate deploy`; `db:migrate:check` сравнивает
  историю миграций со `schema.prisma` и падает при drift. `db:push` остаётся
  только для быстрых локальных экспериментов и не используется в CI/e2e.
  CI применяет миграции на чистой БД и проверяет drift перед полным гейтом.
  Инструкции по backup/restore, cron и обновлению — в `docs/DEPLOYMENT.md`.

**Почему.** Миграции превращают обновление из «надеюсь, `db push` угадает»
в воспроизводимую операцию с журналом. Индексы без привязки к запросам —
налог на запись; выбранные покрывают горячие пути. WAL даёт читателям не
блокировать писателя во время публикации, `NORMAL` остаётся безопасным для
WAL, явный `foreign_keys=ON` гарантирует каскады независимо от сборки
драйвера, а `busy_timeout` превращает краткую блокировку в ожидание, а не в
`SQLITE_BUSY`.

**Цена.** Появилась дисциплина миграций: изменение `schema.prisma` без
`migrate dev --create-only` больше не доедет до БД (тесты на чистой БД это
поймают). WAL создаёт `-wal`/`-shm` рядом с БД — копировать только `.db`
недостаточно, нужен `sqlite3 .backup` или остановка процесса. Индексы
замедляют вставку/обновление записей и занимают место; при росте данных
стоит пересмотреть `Entry`-индексы по фактическому плану запросов.
`db:push` и `migrate deploy` нельзя смешивать на одной БД: после `db push`
`migrate deploy` увидит drift и откажется работать.

### 19. Транзакционный outbox вебхуков

**Контекст.** `fireWebhooks` отправлял события fire-and-forget уже после
коммита: падение процесса, рестарт или временная ошибка получателя теряли
событие без следа, а ретраи жили в памяти и исчезали вместе с процессом.
Изменение контента и факт доставки не были связаны, поэтому «запись
опубликована, но вебхук не ушёл» было штатным исходом.

**Решение.**
- Добавлена модель `WebhookDelivery` со статусами
  `PENDING | DELIVERING | DELIVERED | FAILED`, payload'ом, счётчиком попыток,
  `nextAttemptAt`, `lastAttemptAt`, `deliveredAt`, `responseStatus` и текстом
  ошибки. Удаление endpoint'а каскадно удаляет его доставки.
- `enqueueWebhooks` вызывается **внутри** транзакции изменения контента и
  создаёт по строке на каждый активный endpoint, подписанный на событие.
  Ошибка записи outbox откатывает транзакцию целиком: событие не может
  потеряться при успешно сохранённом контенте.
- `drainWebhookDeliveries` выбирает созревшие доставки пачкой (по умолчанию
  50), затем условным `updateMany` переводит конкретную строку в `DELIVERING`
  и продлевает lease. Параллельные drain'ы (тик, cron, kick после коммита)
  не отправляют одну строку дважды. `nextAttemptAt` у `DELIVERING` — это срок
  lease: если процесс умер, строка снова станет доступной после его
  истечения.
- На один drain выполняется ровно одна HTTP-попытка; расписание повторов
  хранится в БД, поэтому переживает рестарт. Backoff экспоненциальный:
  `WEBHOOK_BASE_BACKOFF_MS × 2^(attempts-1)` (по умолчанию 60 с), но не
  больше 6 часов. После `WEBHOOK_MAX_ATTEMPTS` (8) доставка становится
  `FAILED`. Настраиваются также `WEBHOOK_LEASE_MS` (10 минут) и
  `WEBHOOK_DRAIN_BATCH` (50).
- Если endpoint выключили после постановки события, доставка помечается
  `FAILED` с причиной `Endpoint disabled`, а не повторяется бесконечно:
  оператор явно сказал «не отправлять».
- После коммита `kickWebhookDrain` запускает фоновый drain, не задерживая
  ответ. Независимо от него instrumentation раз в 60 секунд добирает
  `PENDING`, поэтому outbox не зависит от внешнего cron.
  `WEBHOOK_DRAIN_TICK_MS=0` выключает тик; некорректное значение не
  выключает доставку молча, а откатывается к 60 секундам с предупреждением.
  Для внешнего планировщика есть `POST /api/cron/webhooks` с тем же
  `CRON_SECRET`, что и публикация.
- `webhookEndpoint.lastStatus/lastDeliveryAt` по-прежнему отражают последнюю
  попытку; ошибка этого сводного update не скрывает уже зафиксированный
  результат доставки.
- Терминальные доставки старше `WEBHOOK_RETENTION_DAYS` (по умолчанию 30
  дней) удаляются автоматически при тике или cron, не чаще раза в 6 часов
  на процесс. `WEBHOOK_RETENTION_DAYS=0` выключает автоочистку. Неудачная
  очистка не считается выполненной: следующий тик повторит её, а не будет
  ждать ещё 6 часов.
- ADMIN видит последние доставки через `webhook.deliveries`: фильтры по
  endpoint/статусу, лимит до 100 строк. В ответ не попадают `payloadJson`
  и секреты; повторная отправка из UI не предусмотрена — только диагностика.
  Список обновляется кнопкой и после тестового вебхука, без фонового polling.

**Почему.** Outbox делает коммит контента и постановку события атомарными,
а доставку — восстанавливаемой: единственный источник правды о непройденных
событиях находится в SQLite. Условный claim и lease дают корректность при
нескольких процессах/инстансах без внешней очереди. Одна попытка за drain
и backoff в БД означают, что рестарт не ускоряет и не теряет повторы.

**Цена.** Гарантия — at-least-once: процесс может упасть после HTTP-ответа,
но до записи `DELIVERED`, и тогда событие уйдёт повторно; получатель должен
быть идемпотентным. Порядок событий для одного endpoint не гарантируется:
событие с backoff может обогнать более новое, поэтому consumer не должен
опираться на последовательность `entry.updated`. Таблица outbox растёт с
каждым событием на каждый endpoint; терминальные строки автоматически
чистятся по `WEBHOOK_RETENTION_DAYS` (30 дней), но при `0` или выключенных
тике/cron их нужно чистить вручную — см. `docs/DEPLOYMENT.md`. Появляется
задержка до следующего тика, если фоновый kick не успел. Запись outbox
конкурирует с контентом за единственного писателя SQLite; пачка ограничена,
но при большом числе endpoint'ов и событий стоит выносить доставку в
отдельный процесс/очередь.

### 20. Health-проба без утечки деталей

**Контекст.** Для балансировщика и uptime-монитора нужен дешёвый признак
живости. `GET /` отдаёт статический лендинг даже при недоступной БД, поэтому
не отличает рабочее приложение от «процесс поднялся, а данные не читаются».
Админ-панель для этой роли не подходит: она требует сессии и рендерит много
UI.

**Решение.** `GET /api/health` выполняет `SELECT 1` через Prisma и отвечает:
- `200 {"status":"ok","checks":{"database":"ok"}}`, если запрос прошёл;
- `503 {"status":"degraded","checks":{"database":"down"}}`, если БД
  недоступна.

Оба ответа всегда содержат `Cache-Control: no-store`. Наружу не попадают
текст исключения, путь к файлу БД, версии и стек. Маршрут помечен
`dynamic = "force-dynamic"`, чтобы сборка не пыталась выполнить пробу и не
закэшировала результат. Проба намеренно проверяет только БД: без неё
приложение не может обслуживать контент, а проверка uploads/cron/получателей
вебхуков требует отдельных метрик и не должна валить liveness из-за внешнего
сервиса.

**Почему.** `SELECT 1` — минимальная операция, которая проходит через пул
соединений и реально касается SQLite, но не зависит от схемы и объёма данных.
Отдельный статус `degraded` и HTTP `503` позволяют балансировщику снять
инстанс, а монитору — поднять алерт без парсинга лендинга. Отсутствие деталей
в ответе не даёт неаутентифицированному клиенту карту инфраструктуры.

**Цена.** Проба не доказывает, что миграции применены и запросы к таблицам
работают; для этого есть `prisma migrate status`, тесты и логи. При
перегрузке SQLite `SELECT 1` тоже может ждать `busy_timeout`, поэтому таймаут
монитора должен быть больше 5 секунд. Проверка не заменяет метрики outbox,
cron и диска.

### 21. IP клиента за reverse proxy

**Проблема.** Лимиты `/api/v1/*` и `/api/upload` считались по первому адресу
из `X-Forwarded-For`. Этот заголовок полностью контролирует клиент: за
прокси достаточно прислать `X-Forwarded-For: <случайный IP>` перед настоящим
адресом, и каждый запрос получал новое ведро. Прокси добавляет адрес клиента
справа, поэтому левый элемент — не доказательство, а заявление клиента.

**Решение.** `src/lib/client-ip.ts` централизует разбор:
- `TRUSTED_PROXY_HOPS` — число доверенных прокси перед приложением
  (по умолчанию `1`, как в схеме Caddy/Nginx → Next.js);
- клиент — элемент `chain[length - hops]`, то есть адрес, добавленный
  доверенным прокси, а не поддельный префикс;
- выбранный адрес проверяется через `net.isIP`; цепочка короче настроенного
  числа прокси или невалидное значение дают `unknown`, а не произвольную
  строку;
- `TRUSTED_PROXY_HOPS=0` игнорирует и `X-Forwarded-For`, и `X-Real-IP` — для
  прямого подключения без прокси, все клиенты получают общий ключ `direct`;
- некорректное значение переменной откатывается к `1`.

`X-Real-IP` принимается только при отсутствии `X-Forwarded-For` и так же
проверяется. Оба маршрута используют один helper.

**Почему.** Приложение видит только заголовки, а не адрес TCP-соединения,
поэтому единственная надёжная модель — явно объявленное число доверенных
прокси. Правый край цепочки формируют они; левый может сформировать кто
угодно. Валидация IP не даёт превращать произвольные строки в ключи карты
лимитера, а безопасный fallback не ослабляет ограничение при опечатке.

**Цена.** Прокси обязан **добавлять** `X-Forwarded-For`, а не перезаписывать
его одним значением; при нескольких прокси `TRUSTED_PROXY_HOPS` нужно
увеличить, иначе клиенты сольются в адрес ближайшего прокси. Прямое
подключение без прокси требует `TRUSTED_PROXY_HOPS=0`: тогда все запросы
делят один бюджет `direct` — это защита от обхода, но не per-client
справедливость. Настройка не влияет на отдельный rate-limit Better Auth.

### 22. Настраиваемые поля коллекций вместо кода под каждую отрасль

**Контекст.** `Collection.schemaJson` и `Entry.fieldsJson` существовали в
схеме БД, но были мёртвыми данными: UI не давал заполнить схему, а запись
предлагала вводить сырой JSON. Любая отраслевая вариативность (цена, адрес,
дата старта, артикул) требовала новой таблицы/миграции, а сервер не проверял
`fieldsJson` вообще.

**Решение.**
- `Collection.schemaJson` — массив описаний
  `{ key, label, type, required?, placeholder?, help?, options? }`.
  Поддержаны `text`, `textarea`, `number`, `date`, `select`, `checkbox`,
  `url`, `email`; ключ — латиница/цифры/`_`, до 50 полей, дубли и
  несуществующие варианты списка отклоняются.
- Пустая схема `[]` — осознанный легаси-режим: запись хранит произвольный
  JSON-объект, форма показывает JSON-редактор, поля не проверяются. Это
  сохраняет старые коллекции и интеграции без миграции данных.
- tRPC `collection.create/update` принимает структурированные `fields` (для
  UI) или `schemaJson` (совместимость/интеграции). Оба проходят одну
  Zod-проверку; одновременно передавать нельзя. В БД пишется нормализованный
  JSON с явным `required`.
- `entry.create/update` и `POST /api/v1/{collection}` читают схему коллекции
  на сервере и валидируют значения: обязательные поля, диапазон типов,
  `select` только из списка, `checkbox` — boolean (`required` — только
  `true`), дата — реальная календарная дата, URL — только http(s), email.
  Числовые строки нормализуются в числа; пустые необязательные значения
  удаляются.
- Неизвестные ключи значений сохраняются. Схема может эволюционировать, и
  сохранение формы не должно стирать данные, которых в текущей схеме ещё нет.
- UI: конструктор полей (`SchemaEditor`) с перемещением/удалением и
  подсказками, 8 отраслевых шаблонов (блог, услуги, товары, недвижимость,
  мероприятия, команда, документы, портфолио), динамическая форма записи,
  колонки в таблице коллекции, блок «Детали» на публичной странице.
- CSV-экспорт добавляет колонки схемы, а импорт принимает их по ключу или
  названию поля, нормализует типы и пропускает строки, не прошедшие проверку
  (`invalid` в ответе UI). Без колонок схемы импорт остаётся прежним.

**Почему.** Одна и та же механика покрывает любую отрасль без миграции
таблиц: бизнес сам описывает поля, а сервер остаётся границей доверия.
Проверка на сервере, а не только в React, закрывает обход через tRPC и
Headless API. Сохранение неизвестных ключей делает изменение схемы
неразрушающим: старые значения не исчезают при первом сохранении.

**Цена.** Значения лежат в JSON и не индексируются — фильтровать/сортировать
по ним в SQL дорого; для этого нужны явные колонки или отдельный поисковый
слой. Новая обязательная схема не блокирует уже существующие записи до их
следующего сохранения/публикации. Переименование ключа не переносит старые
значения (нужна миграция данных); удаление варианта `select` делает старое
значение невалидным при следующей правке. Смена схемы не создаёт ревизию
записи — история отражает значения, а не описание полей.
