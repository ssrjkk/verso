# Решения (ADR-журнал)

Формат: **проблема → решение → почему → цена**. «Открытых решений» нет:
каждая строка закрыта выбором и кодом.

## P0-A. Роли и регистрация

### 1. Открытый sign-up выдавал ADMIN

**Проблема.** `User.role` имел `@default("ADMIN")`, а Better Auth принимал
`role` из тела запроса. Любой незнакомец получал полные права.

**Решение.** Три слоя:
1. `User.role @default("VIEWER")` в Prisma.
2. В Better Auth `additionalFields.role.input: false` — поле не принимается
   от клиента; `defaultValue: "VIEWER"`.
3. `databaseHooks.user.create.after` вызывает `applySignupRolePolicy`, который
   безусловно фиксирует VIEWER (кроме bootstrap, см. п. 2).

**Почему.** Одного `input: false` мало: при прямом создании пользователя
(импорт, скрипт, будущие плагины) дефолт схемы может быть другим. Слой 3 —
defense in depth и одновременно точка bootstrap.

**Цена.** Два дополнительных UPDATE на регистрацию (один обычно no-op).
Первый пользователь пустой БД всё равно становится ADMIN.

### 2. Bootstrap пустой БД

**Проблема.** Если просто запретить ADMIN при регистрации, свежая установка
остаётся без администратора — управлять нечем.

**Решение.** `applySignupRolePolicy` выполняет один атомарный
`UPDATE "User" SET role='ADMIN' WHERE id=? AND NOT EXISTS (SELECT 1 FROM "User" WHERE role='ADMIN')`.
При параллельных регистрациях ровно один UPDATE изменит строку; остальные
увидит уже существующего ADMIN и останутся VIEWER.

**Почему.** Один SQL-стейтмент атомарен в SQLite/Postgres, не требует
распределённых блокировок и не оставляет окна «два первых админа».

**Цена.** Роль нельзя выбрать при регистрации — только повышение из UI
администратором. Это осознанно.

### 3. Инварианты смены роли

**Проблема.** Понижение последнего ADMIN или смена собственной роли
блокирует систему навсегда.

**Решение.** `setUserRole` (src/lib/roles.ts) в транзакции:
- `targetId === actorId` → `OwnRoleChangeError` → tRPC `FORBIDDEN`;
- demote ADMIN выполняется условным
  `UPDATE ... WHERE role='ADMIN' AND (SELECT COUNT(*) FROM "User" WHERE role='ADMIN') > 1`;
  0 строк → `LastAdminError` → `CONFLICT`.

**Почему.** COUNT вычисляется в момент записи, а не до неё: две параллельные
смены сериализуются SQLite, вторая видит уже одного админа и отказывает.
Проверка «прочитать, потом записать» оставляла гонку.

**Цена.** Demote — raw UPDATE + ORM-дозапись для `@updatedAt`. Роутер ловит
доменные ошибки и переводит в tRPC-коды.

### 4. e2e-БД пересоздаётся на каждом старте

**Проблема.** `e2e.db` накапливал пользователей от прошлых прогонов: старые
sign-up создали десятки ADMIN, инвариант «последний администратор» переставал
быть проверяемым.

**Решение.** `tests/e2e/serve.mjs` удаляет `prisma/e2e.db*` перед
`prisma db push` + seed.

**Почему.** Тесты прав обязаны стартовать с известного baseline; иначе они
проверяют накопленный мусор, а не код. Это же требование «зелёное на свежей
БД».

**Цена.** Данные между прогонами не сохраняются (и не должны). Файлы в
`public/uploads` остаются, но тесты используют уникальные имена.

## Прежние «открытые решения»

### 5. Редиректы не исполнялись

**Решение.** Исполнение переносится в `src/proxy.ts`: точный матч pathname,
только `isActive`, 301/302, TTL-кэш 30 с с инвалидацией при мутации.
Валидация: `toPath` только относительный (`/...`, не `//`, не `/\`),
`fromPath ≠ toPath`, запрет служебных путей, цепочки ≤ 3 и без циклов.
`hits` инкрементится на сервере атомарно; tRPC `incrementHit` удаляется.

**Почему.** Proxy выполняется до рендера и не зависит от клиентского JS;
невалидируемый `toPath` — это open redirect, а публичная mutation накрутки
счётчика — фальсификация аналитики.

**Цена.** Кэш 30 с означает, что изменение редиректа применяется с задержкой
до 30 с (инвалидация — при мутации через приложение).

Реализация: пакет P1-A.

### 6. SCHEDULED не публиковался

**Решение.** `publishDue(now)` (`src/lib/publish-due.ts`): одна транзакция
находит все `SCHEDULED` с `scheduledFor <= now` и для каждой переводит
`SCHEDULED → PUBLISHED` условным `updateMany` (фильтр по статусу и дате) +
`publishedAt` + ревизия (`snapshotJson`, `changeNote: "Публикация по
расписанию"`, `authorId` владельца записи). Вебхук `entry.published` —
только после коммита (fire-and-forget, как в entry.publish).
Триггеры: `POST /api/cron/publish-due` с `CRON_SECRET` (`Authorization:
Bearer`, сравнение SHA-256 + `timingSafeEqual`; без секрета — fail closed
503) и опциональный интервал в `src/instrumentation.ts`
(`PUBLISH_DUE_TICK_MS`, выключен по умолчанию, в edge не стартует).
Время — явный параметр `now` (в проде `new Date()`, UTC ISO-8601).

**Почему.** Планирование без исполнителя — заглушка. Условный флип внутри
транзакции гарантирует: параллельный двойной прогон публикует запись ровно
один раз (второй видит PUBLISHED и пропускает) — ровно 1 ревизия, 1 вебхук.
Повторный прогон ничего не находит — идемпотентность бесплатно. Время явным
параметром вместо `Date.now()` внутри: тесты фиксируют `now` напрямую —
сильнее и стабильнее, чем fake timers поверх реальных SQLite-сокетов
(интеграция идёт на настоящей БД и настоящем echo-сервере).
Fake timers используются там, где уместны: тест регистрации интервала
`instrumentation.register()` (планирование тиков без их исполнения).

**Цена.** В self-hosted без внешнего cron нужен включённый интервал; при
нескольких инстансах возможны лишние тики (идемпотентность их гасит).
Ревизия приписывается владельцу записи (системного пользователя нет —
это осознанно: авторство контента сохраняется).

Реализация: пакет P1-B.

### 7. Нет `task.remove`

**Решение.** `task.remove` (`protectedProcedure` + проверка): автор задачи
(`assigneeId === self`) или привилегированная роль (ADMIN/MANAGER). VIEWER
чужую задачу удалить не может (`FORBIDDEN`), несуществующая — `NOT_FOUND`.
Кнопка удаления в календаре (с `confirm()`), сервер решает окончательно.

**Почему.** Созданную задачу нельзя было убрать — таблица росла мусором.
Авторство, а не только роль: VIEWER может быть исполнителем и должен уметь
убрать свою задачу, но не чужую.

**Цена.** Удаление без корзины (задача — операционный объект, не контент).

### 8. Нет UI редактирования коллекций

**Решение.** Inline-редактирование карточки: `name` и `description`
(`collection.update`, только ADMIN; кнопка видна только ADMIN).
`slug` в форме — только текст: после создания read-only и в API
(вход `update` slug не принимает), и в UI.

**Почему.** Slug — часть URL Headless API (`/api/v1/{collection}`); его смена
ломает интеграции и опубликованные ссылки. Переименование отображаемого имени
безопасно.

**Цена.** Опечатку в slug нельзя исправить из UI — только миграцией/скриптом
с пониманием последствий.

### 9. Headless-ключи в query и безлимитные ручки

**Решение.** `?key=` удалён: ключ принимается только из `x-api-key` или
`Authorization: Bearer` (query оседает в логах/CDN). READ-ключ видит только
PUBLISHED (как и раньше), запись — 403. `lastUsedAt` перезаписывается не чаще
раза в минуту (телеметрия, а не часы: каждый GET не должен дёргать строку).
Token bucket в памяти (`src/lib/rate-limit.ts`, `now` явным параметром):
`/api/v1/*` — 240/мин на IP, `/api/upload` — 60/мин на пользователя;
превышение — 429 + `Retry-After` в секундах. In-memory осознанно:
single-instance SQLite, у каждого инстанса свой бюджет (fail-open в сторону
доступности; аутентификация от лимита не зависит).

**Почему.** Ключ в URL — утечка по дизайну; безлимитные ручки — флуд, перебор
и забивание диска.

**Цена.** In-memory бюджет не делится между инстансами; легитимный всплеск
сверх лимита получит 429 и должен повторить после `Retry-After`.

### 10. Загрузки: только реальные файлы под случайными именами

**Решение.** `validateUploadFile(file, bytes)` — сигнатура файла обязательна:
PNG/JPEG/GIF/WEBP/PDF/MP4 + AVIF/WEBM проверяются по magic bytes реальных
байтов (нулевой/текстовый контент под видом картинки — 400). Имя на диске —
всегда `randomUUID().ext` (коллизий, traversal и утечек имён нет); в БД
оригинальное имя хранится только для отображения (экранируется React, в путях
не используется). `sizeBytes` — реальные байты, не заявление клиента.
`media.create` (прямая запись) валидируется тем же модулем: URL обязан быть
`/uploads/<folder>/<uuid>.<ext>` из управляемого набора, mime — соответствовать
расширению, размер — в лимите. SVG/HTML/JS по-прежнему запрещены (stored XSS
в origin CMS).

**Почему.** Расширение и MIME подделываются одной строкой; без magic check
«картинка» с HTML-внутреностями ложится в `/uploads` и отдаётся с тем же origin. Произвольный `media.create` позволял записать любой URL
с любым mime/size в обход всех проверок загрузки.

**Цена.** Нестандартные, но валидные файлы с повреждёнными заголовками
отклоняются; AVIF требует `ftyp`+`avif`-бренд (обычный mp4 под видом avif
не проходит).

### 11. P3: a11y/контраст/скриншоты

**Решение.** `@axe-core/playwright` — dev-зависимость (обоснование: пакет P3
требует axe-проверку «0 serious/critical»; в рантайм не попадает).
Скриншоты: 12 страниц × 3 вьюпорта (375/768/1440) × светлая/тёмная тема —
72 + empty/skeleton, итого 74 файла в `test-results/screenshots/` (gitignore,
в индекс не попадают). Проверки в `tests/e2e/visual-a11y.spec.ts`:
- нет горизонтального скролла на каждой комбинации (documentElement);
- axe: 0 serious/critical на каждой странице в обеих темах (включает
  color-contrast ≥4.5:1 для обычного текста);
- empty state и skeleton коллекций (перехват tRPC: пустой список / задержка);
- клавиатура: Tab-порядок без потери фокуса, фокус-кольцо `#f97316`
  (`:focus-visible` в globals.css, проверено по computed style);
- Esc закрывает командную палитру (Ctrl+K открыть);
- dnd-kit KeyboardSensor на `/board` (Space — взять, Esc — отмена) и ручки
  сортировки в билдере (`title`+`aria-label`).

**Контраст: палитра текста.** Белый текст на фирменном `#f97316` даёт 2.8:1 —
ниже AA, поэтому все текстовые CTA-поверхности переведены на тёмный оттенок
того же hue: `bg-[#c2410c] hover:bg-[#9a3412]` (белый текст 5.0:1).
Оранжевый текст на светлом: `text-[#9a3412] dark:text-[#f97316]`
(тёмная тема оставлена как была — там контраст и так проходит).
Красный текст: `text-red-600 dark:text-red-500`. Всегда-тёмные auth-страницы
(`bg-[#12121a]`) не трогали — там `#f97316`-текст проходит.
Исправлены по ходу 3 настоящих переполнения: `min-w-0` на main (grid blowout),
на flex-враппере таблицы коллекций и на aside календаря; `min-w-0 w-full`
на селектах формы задач; `min-w-0` на кнопках-днях календаря.

**Почему.** Оранжевый бренд остаётся для акцентов/колец/бейджей-фонов, но
текст обязан читаться по WCAG AA. axe — арбитр: список выше — это ровно то,
что он флаговал, плюс labels/selects (`select-name`, `label`,
`label-title-only`, `label-content-name-mismatch` — всем контролам даны
доступные имена).

**Цена.** CTA-кнопки темнее фирменного чипа (тот же hue, темнее оттенок);
`@axe-core/playwright` тянет браузерный axe-core в dev-зависимости.

### 12. P4: чистая установка обязана работать с первого раза

**Решение.** `better-sqlite3` зафиксирован на `^12.11.1` (единственная
дедуплицированная копия; nested-дубль от адаптера исчез).
v13 поставляет bundled prebuilds с `gypfile:false`, но npm всё равно
синтезирует `node-gyp rebuild` при наличии `binding.gyp` и падает на машинах
без VS Build Tools — чистый клон на Windows не ставился вообще. У v12
`prebuild-install || node-gyp rebuild` скачивает готовый бинарник
(проверено: exit 0). Версия совпадает с той, что резолвит себе
`@prisma/adapter-better-sqlite3@7.10.1`, сырой импорт (`new Database`)
используется только в одном e2e-сидтесте и с v12 совместим.
Плюс хуки `predb:seed`/`predev` → `prisma generate`: README-поток
`db:push → db:seed` падал на чистой копии (`Cannot find module
.prisma/client/default`). CI (`ci.yml`) выполняет ровно ворота
`test:all` (typecheck + vitest + build + e2e) после `npm ci` и установки
Chromium.

**Почему.** P4 требует зелёный `test:all` на голом клоне; зависимость,
требующая компилятор C++ на машине разработчика, — скрытый стопор.
Дефект всплыл только на чистой копии (в рабочем дереве node_modules был
собран раньше).

**Цена.** Остаёмся на v12 вместо v13 (N-API, разницы в используемых API нет);
`npm ci` тянет prebuild через сеть (как и любой пакет).

Dependabot повторно предложил v13 (`2a331c4`); при проверке установки
на Windows `npm install` снова упал на `node-gyp rebuild` без VS Build Tools,
поэтому версия возвращена к `^12.11.1`. ADR остаётся в силе: обновление
до v13 допустимо только вместе с решением проблемы prebuild на Windows.

### 13. Публичные страницы соответствуют sitemap

**Решение.** Реализованы RSC-маршруты `/c/[slug]` (список коллекции) и
`/p/[collection]/[slug]` (запись). Оба читают только `status = PUBLISHED`:
черновики, записи вне публикации и несуществующие slug'и отдают `404`.
Запись рендерит только видимые блоки (`isVisible`, `order asc`) через
`BlockRender`, показывает дату публикации и теги; `generateMetadata`
использует `seoTitle`/`seoDescription`/`ogImageUrl`/`canonicalUrl`/`noIndex`.
Запросы обёрнуты в React `cache()`, чтобы `generateMetadata` и рендер не
делали два одинаковых чтения. Список коллекции — первые 50 опубликованных
записей, новые сверху.

**Почему.** `sitemap.xml` уже публиковал `/c/` и `/p/`, но маршрутов не было:
поисковики и пользователи получали 404. Продукт — CMS с публичной доставкой,
поэтому чинить нужно страницами, а не удалением URL из карты сайта.

**Цена.** Публичные страницы читают SQLite на каждый запрос (без ISR);
при росте трафика понадобится `revalidate`/кэш. Список ограничен 50
записями без пагинации.

### 14. CI не зависит от apt при установке Chromium

**Решение.** В `ci.yml` используется `npx playwright install chromium` без
`--with-deps`: образ `ubuntu-latest` уже содержит системные библиотеки.
`--with-deps` каждый раз ходит в `archive.ubuntu.com`; при DNS-сбое раннера
job падает до запуска тестов (наблюдалось дважды подряд).

**Почему.** Установка браузера не должна быть точкой отказа CI из-за
чужого apt-зеркала.

**Цена.** Если GitHub уберёт библиотеки из образа, шаг придётся вернуть
или ставить зависимости точечно.

### 15. Статические проверки: ESLint + покрытие в общих воротах

**Решение.** Добавлен ESLint 9 с flat-config `eslint.config.mjs`:
`eslint-config-next/core-web-vitals` + `eslint-config-next/typescript`.
`npm run lint` включён первым шагом `test:all`, поэтому CI проверяет его
до типов и тестов. Покрытие (`@vitest/coverage-v8`, `npm run test:coverage`)
тоже включено в `test:all`; отчёт считает весь `src`, пороги —
45% statements/lines, 42% branches, 32% functions. UI-страницы остаются
преимущественно за e2e (83 сценария: рендер, 404, axe, скриншоты,
клавиатура), поэтому общий процент ниже серверного слоя.

TypeScript 7 не предоставляет API для typescript-eslint. Использован
официальный side-by-side рецепт из анонса TS 7: `typescript` — npm-алиас
на `@typescript/typescript6` (API для ESLint/Next), `@typescript/native` —
алиас на `typescript@7`, который даёт быстрый `tsc`. `npm run typecheck`
по-прежнему идёт через TS 7 (`npx tsc --version` → 7.0.2).

**Почему.** До этого в проекте не было линтера, а `next build` в Next 16
больше не запускает ESLint автоматически: ошибки React hooks/Next правил
могли попасть в main незамеченными. Покрытие без порога — отчёт, который
никто не обязан читать; порог превращает его в проверку.

**Цена.** ESLint и typescript-eslint добавляют dev-зависимости и ~10 с к
прогону. Порог покрытия может потребовать теста при добавлении крупного
непокрытого модуля — это осознанно. Алиас `typescript` на TS 6 нужен
только инструментам; сборка/типы используют TS 7. Для устранения
moderate-уязвимости `minimatch@10` (DoS через globparts) добавлен точечный
npm-override `@typescript-eslint/typescript-estree → minimatch@^11.0.8`;
`npm audit` снова даёт 0 уязвимостей.
